# HTTP API

Две группы, как требует ТЗ: приём транзакций для банковских систем и клиентская часть.

## Приём транзакций

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/transactions` | принять одну расходную операцию |
| `POST` | `/api/v1/transactions/batch` | принять до 100 сразу, разрешая курсы параллельно |

```json
{
  "account_from": "0000000123",
  "account_to": "9999999999",
  "currency_shortname": "KZT",
  "sum": 10000.45,
  "expense_category": "product",
  "datetime": "2022-01-30T00:00:00+06:00"
}
```

Батч принимает то же тело в виде массива и отвечает массивом таких же ответов, в том порядке, в
котором они пришли. Параллельно выполняются только поиски курсов; флаг по-прежнему выставляется
по одной транзакции под блокировкой строки лимита, поэтому батч даёт те же ответы, что и те же
транзакции, отправленные по одной и в том же порядке. Транзакция в валюте без доступного курса
сохраняется с `limit_calculated: false`, а не отклоняет батч; неизвестная валюта отклоняет, потому что
к этому моменту предыдущие транзакции уже записаны, и частичная запись, объявленная ошибкой, была бы
ложью.

## Клиентский API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/limits` | установить новый лимит |
| `GET` | `/api/v1/limits?account_from=` | лимиты с уже потраченной суммой |
| `GET` | `/api/v1/limits/exceeded?account_from=&month=` | транзакции, превысившие лимит |
| `GET` | `/api/v1/currencies` | коды валют, которые сервис принимает |
| `GET` | `/api/v1/currency-pairs` | валюты, которые ежедневный свип опрашивает |
| `PATCH` | `/api/v1/currency-pairs/{code}` | включить или выключить свип для валюты |

Два эндпоинта про валюты отвечают на разные вопросы, и их легко спутать: `/api/v1/currencies`
отдаёт **весь справочник** — что вообще можно прислать в транзакции, — а `/api/v1/currency-pairs`
только отслеживаемый свипом подмножество с признаком `active`. Всё остальное принимается, курс
просто будет взят по требованию.

`PATCH /api/v1/currency-pairs/{code}` принимает `{"active": true|false}`. Именно `PATCH`, а не
`PUT`: меняется один атрибут одного ресурса, а не ресурс целиком. Значение, которое уже установлено,
возвращает `200`, а не конфликт, — повтор запроса не должен падать.

`POST /api/v1/limits` принимает `account_from`, `expense_category` и `sum`. Поля даты нет: время
установки — всегда «сейчас», и именно это делает невозможным бэкдейт. Обновление существующего лимита
запрещено спецификацией — эндпоинта для этого просто нет.

`GET /api/v1/limits/exceeded` возвращает каждую транзакцию с `limit_sum`, `limit_datetime` и
`limit_currency_shortname`. Это тот лимит, по которому флаг считался на самом деле, а не тот, который
случайно действует сейчас, — поэтому лимит и хранится на строке транзакции.

## Имена полей

Имена на проводе — те, что заданы таблицами ТЗ: `account_from`, `account_to`, `currency_shortname`,
`sum`, `expense_category`, `datetime`, а в ответе плюс `limit_sum`, `limit_datetime`,
`limit_currency_shortname`. Один регистр для тела, параметров запроса и ответа.

На входе каждое многосложное поле дополнительно принимает camelCase-написание (`accountFrom`) через
`@JsonAlias`: сервис встраивается в банковскую систему, которая уже что-то отправляет, и одно поле
стоит дешевле, чем сломать её. **На выходе camelCase нет** — два начертания в ответе означали бы
контракт, на который нельзя положиться.

Имена приходят не из имён компонентов record: их переименовывает `@JsonNaming` на каждом DTO, и
`features/rule/wire_contract.feature` сверяет результат с таблицами документа. Ошибка Bean Validation
тоже называет поле так, как его прислал клиент, — иначе 400 указывал бы на поле, которого в запросе
нет.

## Ошибки

Все ошибки — `application/problem+json` (RFC 9457), собираются в одном месте,
`exception/GlobalExceptionHandler`. Нарушения Bean Validation добавляются по полям в свойстве
`errors`.

Контроля доступа нет ни на одном эндпоинте: ТЗ требует именно прототип «без разграничений доступа
к API». **Это допустимо только в рамках задания** — см. [`assumptions.md`](assumptions.md).

## Документация

Интерактивная — `/swagger-ui.html`, JSON — `/v3/api-docs`, YAML — `/v3/api-docs.yaml`. У каждого поля
есть описание и пример; заголовок, версия и описание API берутся из `OpenApiConfiguration`. У каждого
обработчика есть `@Operation` с описанием того, чего не видно из имени метода: какой лимит вернёт
строка, почему флага может не быть, какую дату выбрал сервис.

Вне профиля `dev` Swagger и `/v3/api-docs` выключены — в проекте нет контроля доступа, и открытый на
проде `api-docs` отдал бы любому, кто дотянулся до порта, полное описание внутренней поверхности.
Клиенты получают контракт артефактом сборки: `quality.yml` поднимает контейнер в профиле `dev` и
выкладывает JSON как артефакт `openapi-contract`.

## Ограничения частоты

Приём транзакций и установка лимитов ограничены по адресу вызывающего. За превылением квоты — `429`
с `ProblemDetail` и заголовком `Retry-After`. Числа живут в `application.yml` под `app.rate-limits` как
«разрешений за период»; аннотация `@RateLimited` называет только блок.

Ограничитель — resilience4j `RateLimiter`, вызываемый программно, а не через `@RateLimiter`: та
аннотация — аспект, строящий **по одному ограничителю на метод**, то есть квота на метод, а не на
вызывающего. Перехватчик создаёт и кэширует ограничитель по адресу и зовёт `acquirePermission()` с
нулевым таймаутом, чтобы отказ происходил сразу: клиенту, которому сказали подождать, нужен ответ с
`Retry-After`, а не занятый поток.

Квота привязана к адресу, а не к счёту, и это стоит проговорить прямо: счёт едет в теле JSON, а
ограничитель частоты срабатывает до того, как тело прочитано. Понадобился бы либо фильтр, который
сначала буферизует тело, либо заголовок с аккаунтом, и ни того, ни другого здесь нет.

Ограничители живут в памяти, поэтому несколько инстансов умножают эффективную квоту. Для сброса
нагрузки на узел это правильная форма, для глобального потолка — неправильная.
