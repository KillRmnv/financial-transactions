# Эксплуатация

## Запуск

Нужны JDK и Docker. Тестам нужен Docker под Testcontainers: они поднимают свои PostgreSQL и Redis и
compose-файл не используют.

Pom нацелен на Java 25.

```bash
export JAVA_HOME=/usr/lib/jvm/java-27-openjdk
./mvnw verify                 # компиляция, тесты, SpotBugs
./scripts/ci.sh               # то же плюс проверка формата
./scripts/ci.sh --fix         # переформатировать вместо проверки
./mvnw spring-boot:run        # нужны PostgreSQL и Redis, см. ниже
```

Приложение отказывается стартовать без `DataSource`, поэтому вне тестов нужно поднять PostgreSQL и
Redis:

```bash
cp .env.example .env          # локальные учётные данные, .env в gitignore
docker compose up -d db redis # только зависимости

set -a && . ./.env && set +a  # POSTGRES_* и RATES_* в окружение

SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/${POSTGRES_DB} \
SPRING_DATASOURCE_USERNAME=${POSTGRES_USER} \
SPRING_DATASOURCE_PASSWORD=${POSTGRES_PASSWORD} \
SPRING_DATA_REDIS_HOST=localhost \
./mvnw spring-boot:run
```

Подстановка `.env` вместо копирования трёх значений руками держит ключ и compose-стек в шаге: URL
собирается из тех же `POSTGRES_*`, с которыми поднялся контейнер базы, поэтому разъехаться в
connection refused они не могут.

С ключом `RATES_API_KEY`, заданным `RATES_API_BASE_URL` и доступным провайдером приложение берёт
курс по требованию для валюты, которую видит впервые. С пустым ключом — нет: провайдер не
регистрируется, и все курсы берутся из базы, что на холодном старте правильно, а если вы имели в виду
не это — сбивает с толку.

Или поднять всё сразу, сервис включён:

```bash
docker compose up --build -d
curl http://localhost:8080/actuator/health
docker compose down -v
```

## Проверка на живом провайдере: три вещи, которые выглядят как баги

**Датируйте транзакции недавними датами.** Это отнимает больше всего времени. Бесплатный тариф
Twelve Data хранит примерно **год истории**, а все даты в спецификации — январь и февраль **2022**.
Транзакция от `2022-01-30` вернёт

```json
{ "sumInLedger": null, "limitExceeded": null, "limitCalculated": false }
```

и это не поломка. Курс ищется за **первый день месяца**, то есть провайдеру запрашивается
`2022-01-01`, а он отвечает `No data is available on the specified dates`. Замерено на живом API:
`2024-01-02` — данных нет, `2025-06-02` — есть, `2026-09-01` — есть. Поставьте дату в последние
месяцы — тот же запрос вернёт сконвертированную сумму и флаг.

**Следите за квотой.** Бесплатный тариф разрешает **8 запросов в минуту**. После исчерпания провайдер
отвечает пустым телом, импорт пишет в лог `answered the currency search with no data`, а запрос курса
тихо превращается в транзакцию без флага. Помогает минута ожидания; код не помогает ничем.

**История ограничена тарифом, а квота ограничена тарифом — и только второе выглядит как ошибка.**

| Что пробовали | Что приходит |
|---|---|
| `KZT` датой 2022 | `limitCalculated: false` — истории так далеко нет |
| `KZT` датой 2026-10-03 (суббота) | конвертируется — валютные пары торгуются и в выходные |
| валюта, которую провайдер не котирует | `404`, понятная problem-detail |
| 10 запросов за минуту | пустое тело, транзакция без флага, без ошибки |

## Конфигурация

Всё внешнее живёт под `app.*` в `application.yml` или в окружении. Ни URL, ни учётных данных, ни квот,
ни часовых поясов не захардкожено.

| Свойство | По умолчанию | Смысл |
| --- | --- | --- |
| `app.month-timezone` | `UTC` | единственный часовой пояс, в котором считаются границы месяца |
| `app.ledger.currency-code` | `USD` | валюта учёта: суммы лимитов и `ledger_sum` |
| `app.ledger.amount-scale` | `2` | знаков после запятой у денежной суммы |
| `app.default-limit-sum` | `1000.00` | лимит, когда клиент ничего не устанавливал |
| `app.rates.providers.<имя>.base-url` | — | адрес провайдера; пусто — он не регистрируется |
| `app.rates.providers.<имя>.api-key` | — | ключ; необязателен, у Frankfurter его нет |
| `app.rates.providers.<имя>.source` | имя блока | как провайдер называется в `currency_rate.source` |
| `app.rates.providers.<имя>.order` | — | кто спрашивается первым, меньше раньше |
| `app.rates.providers-enabled` | `true` | общий выключатель блока; сьюты с заглушкой ставят `false` |
| `app.rates.connect-timeout` / `read-timeout` | `3s` / `5s` | таймауты внешнего запроса, общие для всех провайдеров |
| `app.rates.attempts` / `retry-backoff` | `3` / `500ms` | повторы при сбое внешнего API |
| `app.scheduled-fetch-hour` | `7` | час суточного обхода в `app.month-timezone` |
| `app.scheduling.enabled` | `true` | регистрировать ли задачи по расписанию вообще |
| `app.scheduling.weekly-currency-import.cron` | `0 30 4 * * MON` | расписание импорта ISO 4217, cron из шести полей |
| `app.rates.fallback-days` | `10` | за сколько дней назад искать курс, когда за день его нет |
| `app.cache.enabled` / `ttl` / `key-prefix` | `true` / `12h` / `financial:rate:` | кэш курсов |
| `app.rate-limits.<блок>` | — | квоты приёма по адресу вызывающего |

## Переменные окружения

| Переменная | На что влияет |
| --- | --- |
| `SPRING_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD` | подключение к базе |
| `SPRING_DATA_REDIS_HOST` | кэш курсов |
| `SPRING_PROFILES_ACTIVE` | `dev`, `prod` или пусто |

| `RATES_API_KEY` | ключ провайдера |
| `POSTGRES_DB` / `_USER` / `_PASSWORD` | параметры контейнера в compose |
| `DEPLOYMENT_ENVIRONMENT` | попадает в логи и метрики |
| `JAVA_TOOL_OPTIONS` | флаги JVM, которые нужны развёртыванию без пересборки образа |

`RATES_API_KEY` в `.env.example` — пустая строка: реальный ключ в репозиторий не попадает.

## Флаги JVM

Задаются через `JAVA_TOOL_OPTIONS`, потому что JVM читает их сам и так развёртывание может их
переопределить без пересборки образа:

```
-XX:MaxRAMPercentage=70
-XX:MaxMetaspaceSize=128m
-XX:+HeapDumpOnOutOfMemoryError
-XX:+ExitOnOutOfMemoryError
-XX:HeapDumpPath=/app/dumps
-XX:ErrorFile=/app/dumps/hs_err_pid%p.log
```

`MaxMetaspaceSize` — отдельный потолок, потому что процент кучи метаспейс не покрывает, а неограниченный
убивает контейнер, куча которого никто не трогал. **`JAVA_TOOL_OPTIONS` несёт диагностику, а не
настройку памяти** — потому что её чаще всего и нужно переопределить в развёртывании.

**Флага, который дампит кучу при падении JVM, не существует.** У HotSpot такого механизма нет:
нативное падение разбирается по журналу `hs_err`, на который указывает `-XX:ErrorFile` в той же папке.
Дамп размером с кучу и содержит учётные данные, поэтому `/app/dumps` хочет volume.

## Память, потоки, соединения

**Куча `MaxRAMPercentage=70`, бюджет 1 ГБ.**

Процент кучи без `mem_limit` бессмысленен: контейнер без лимита видит память хоста, и «70 %» становится
долей от того, на чём машина оказалась — здесь замерено 11,7 ГБ на неограниченном запуске против 718 МБ
при `-m 1g`. `UseContainerSupport` включён по умолчанию с JDK 10, JVM читает cgroup-лимит сам, и
`-XX:+UseContainerSupport` не нужен.

Проверять кучу надо через `jcmd` или `-Xlog:os+container`, а не через `jvm.memory.max`: под G1 эта
метрика отдаёт **только старое поколение** — около 250 МБ на контейнере с `MaxHeapSize` 718 МБ.

**Три числа — одно решение с тремя цифрами**, и они стоят рядом в `application-prod.yml`:

| Параметр | Значение | Почему |
| --- | --- | --- |
| `maximum-pool-size` | 20 | соединение — дефицитный ресурс: каждый запрос, трогающий флаг, держит его, пока читает итог, а занятое держит дольше, ожидая блокировку |
| `minimum-idle` | 5 | не 15: после этого — честный конец, дальше клиенту говорят, что сервис занят, вместо того чтобы парковать его на пять секунд и сказать то же самое |
| `connection-timeout` | 1000 мс | короткий таймаут намеренно: за ним клиента уведомляют о занятости, а не держат |
| `server.tomcat.threads.max` | 40 | вдвое больше пула: при 200 потоках Tomcat против пула в 20 живут 180 потоков, которые ничего не делают, кроме ожидания соединения |

Значения связаны между собой, и `hikaricp.connections.pending` и `.timeout` растут ровно тогда, когда
пул является ограничением.

**Каждое подключение держит соединение, поэтому `replicas × 20 + 3 + миграции < max_connections`.** При
compose-значении по умолчанию 100 это три реплики, а не пять. За пределом симптом — не ошибка, а
зависание: соединения выстраиваются в очередь внутри базы, а приложение сообщает о себе, что
здорово. Повышение `max_connections` откладывает это, но не чинит; пулер убирает, и это отдельное
решение.

**`idle-timeout` обязан быть меньше `max-lifetime`,** и отказ от этого тихий: Hikari *отключает* idle
timeout и пишет одно предупреждение, которое читается как совет о другом. Оба равны 600000 — и
`idle-timeout` просто перестаёт существовать.

**Виртуальные потоки в `prod` выключены, намеренно.** На Tomcat они переносят узкое место в HikariCP:
число запросов становится неограниченным, а пул остаётся из двадцати соединений, поэтому задержка
становится **хуже**, а причина не видна на дашборде. `server.tomcat.threads.max` перестаёт что-то
значить, `jstack` перестаёт показывать потоки запросов, и медленный запрос больше не убивается по
`connectionTimeout`. Суточный обход виртуальные потоки использует в любом случае — там они окупаются,
и никакого общего пула там нет.

## Профили

| Профиль | Отличия |
| --- | --- |
| без профиля | локальная разработка, всё внешнее через переменные окружения |
| `dev` | Swagger и `/v3/api-docs` включены, подробные логи, щедрые квоты |
| `prod` | Swagger выключен, actuator `heapdump` выключен, пул 20, потоков 40, `lock_timeout` 3 с, graceful shutdown |

Вне `dev` эндпоинт `heapdump` и Swagger выключены. Дамп — полная копия процесса, поэтому открытый
где-либо общем он отдаёт всё, что в памяти; `/v3/api-docs` — вторая половина той же проблемы,
описывающая всю внутреннюю поверхность вместо двух документированных API. springdoc предупреждает о
втором при каждом старте в проде, и он прав.

**`server.shutdown: graceful` с фазой в 30 с.** По умолчанию запросы в полёте обрываются немедленно, а
для этого сервиса это значит прерывание транзакции, возможно держащей `PESSIMISTIC_WRITE` на строке
лимита: транзакция откатывается, клиент получает 500, и развёртывание, вызвавшее рестарт, выглядит
причиной аварии.

## Метрики и диагностика

`/actuator/health`, `/actuator/metrics`, `/actuator/prometheus`.

| Метрика | Что показывает |
| --- | --- |
| `financial.transactions.accepted{outcome}` | принятые транзакции по исходу: с флагом, без курса, с превышением |
| `financial.rates.resolved{source,provider}` | откуда взят курс: `cache`, `database`, `provider` |
| `financial.rates.lookup` | таймеры поиска курса с source и provider |
| `financial.sweep.duration` | длительность суточного обхода |
| `hikaricp.connections.*` | состояние пула; `.pending` и `.timeout` растут, когда пул стал ограничением |

**Micrometer регистрирует метрики Hikari как `hikaricp.*`, а не `haki‌ri.*`.** Дашборд с запросом
`hikari.connections.pending` покажет пустую серию вместо ошибки, поэтому ошибку не видно. Метрик потоков
Tomcat в Boot 4 нет вообще, есть только `tomcat.sessions.*`; число потоков берётся из
`jcmd <pid> Thread.print | grep -c http-nio`, и это диагностика, а не то, что стоит скрейпить.

## Docker

`Dockerfile` — многостадийная сборка на базе `eclipse-temurin` без изменений. Обрезанный через `jlink`
runtime на distroless-базе пробовали и откатили: работает и экономит около трети размера образа, но
требует список модулей, который верен ровно до следующей зависимости, и неверный элемент падает при
первом запуске, а не на сборке.

`curl` в runtime-слое не опционален: его используют и `HEALTHCHECK`, и smoke-проверка в CI, а temurin
JRE не содержит `wget`.

Локально `docker build -t financial-transactions:local .` первый раз занимает несколько минут. В
compose Redis несёт `maxmemory 64mb` и `allkeys-lru`: политика по умолчанию — `noeviction`, поэтому
переполненный Redis отказывает, а не вытесняет — кэш перестаёт помогать, оставаясь оплаченным, и
приложение корректно откатывается к базе.
